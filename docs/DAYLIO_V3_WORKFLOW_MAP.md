# Daylio Backend v3 workflow map

Existing repository and service boundary retained. `app/workspace/operations.tsx` is the role-specific client of the existing `/api/v1` handler and `lib/service.mjs`; `?tools=1` retains the earlier administrative screens. These are views of the same records and authenticated organization, not another application. The reference prototype is never imported into runtime code.

| Journey / matrix | State transitions | Who acts | Persistent evidence and guards |
|---|---|---|---|
| Quick Care / F09,F10,F12,F13,F15 | Current class attendance → selected present children → per-child drafts with shared server batch ID → explicit group publication | Assigned caregiver or management; manager reviews when owner policy requires it | Assignment and attendance verified for every child before any insert. Common result plus individual overrides. POST retry key retained for unchanged failed submissions; HTTP replay rechecks current role/policy and child authorization. Corrections create immutable record history and return published activities to draft. |
| Morning handover / F16,F18,F20 | Parent submitted → staff acknowledged; editing resets to submitted | Linked guardian creates/edits own note; assigned caregiver or management acknowledges | Actor, date, acknowledgment time and actor, record history, management notification. Parent sees own note and acknowledgment. |
| Daily Story / F12,F15,F16,F18 | Published same-child/day activities → human-written draft → explicit publish | Assigned author under routine policy or management | Source IDs verified on create and publish; one story per child/day. Per-child daily bundle notification deduplicated across published activities/story. No generated milestones. |
| Exceptions / F19,F20,F21 | Open source records → contextual review/action; closing creates separate immutable-history snapshot | Management | Open incidents, morning notes, pending pickup, policy review drafts, observations, passport proposals and shift handoffs remain their original states until acted on. Closing stores unresolved references and does not check children out or assert safety. |
| Routine pickup / F08,F10,F11 | Linked guardian permission → approved → staff verifies real person → handover + attendance out | Guardian authorizes; assigned staff verifies and physically hands over | Validity window, optional allowed weekdays, guardian link rechecked, verified name must match, method and minimal identity note required, explicit handover confirmation. Child advisory lock + unique check-in-cycle evidence prevent double handover. Routine authorization reusable on a subsequent attendance cycle. |
| Substitute pickup / F08,F10,F11 | Guardian requested → manager approved (unless explicit owner policy permits direct guardian approval) → physical ID verification → used | Guardian, management, assigned handover staff | Expired/revoked/used permissions denied. Substitute always requires physical ID method. Server records guardian, permission, staff, time, check-in and checkout evidence; no camera/identity inference. |
| Care Passport / F07,F08,F38 | Guardian proposal submitted → manager approve/reject → current approved version | Linked parent proposes; management decides; assigned staff reads | Source proposal, approved actor/time, version, emergency contact, history and notification. Proposal never silently replaces current passport. Enrollment-created profiles explicitly identify incomplete onboarding. |
| Development / F07,F15,F16,F22,F32 | Dated observation draft → submitted → management approved/rejected → report draft from approved observations → human sign-off → published → private PDF | Assigned educator observes; management reviews/assembles/signs; linked parent reads published reports | Configured rubric version/domain and age band checked against birth date. Same child/period approved sources only. Daily-care notes cannot be substituted for approved observations. Source snapshots, reviewer and publisher retained. PDF generated after current authorization. |
| CRM / F23–F26 | Inquiry → staff notes/status → optional tour/trial → confirmed class slot, package, emergency contact → atomic existing enrollment/invitation | Owner or explicitly CRM-delegated manager | Existing lead/tour/trial/followup services retained. Capacity lock before conversion; old retry-safe enrollment remains. Guardian access starts only after verified invitation acceptance. Advanced qualification fields and calendar UX remain tracked separately. |
| WhatsApp / F23,F26 | Staff-authored draft → copy/open action | CRM-authorized human | Stored text, purpose and lead reference; copy/open audited. Delivery always `not-sent`; no consumer WhatsApp automation or provider claim. |
| Owner / F21,F26,F31 | Persisted roster, capacity, attendance, published stories and lead state → Business Pulse | Owner; operational metrics available to management under RLS | No fixture counts in normal accounts. Unknown capacity stays unknown. Date/branch dimensions and limitations documented; historical state reconstruction is not implied. |
| LEO / F30–F32 | Authorized structured records → deterministic sourced response; human must separately publish | Parent published own-child facts; caregiver assigned-child facts; management authorized aggregates | Provider explicitly not connected. Stored notes are returned as data, never executed as instructions. Existing draft-summary and manual approval API retained. |

Security is enforced by the original provider-verification boundary, organization transaction context and PostgreSQL RLS. Migration 011 narrows manager finance/CRM/security permissions and adds care policy, consent and new typed kinds. Parent, staff and manager menus do not grant permissions by themselves. Photo upload, grant and content access require consent for each declared depicted child; access rechecks consent and current links.

## Evidence and environment

- `tests/v3-workflows.test.mjs`: thirteen PostgreSQL-backed cross-role workflow tests, in addition to the retained F01–F42 regression suite; 36 total passing tests.
- `scripts/browser-v3-test.mjs`: real UI login and care, morning, sibling, review, pickup and closing journeys; authenticated HTTP replay; responsive screenshots. Results are recorded only when the script succeeds.
- `scripts/browser-v3-business-test.mjs`: real passport, rubric/observation/report/PDF, CRM qualification/unsent WhatsApp/price-confirmed enrollment, and parent/caregiver/owner LEO UI journeys. No external messages sent.
- Local sandbox uses a versioned, synthetic-only fixture behind the existing production prohibition. It is not hosted Supabase or a production provider test.
- Role-sensitive views retain loading, honest empty states, offline/retry messages and explicit confirmations. No role selector or localStorage record store is used in the operations client.

## Remaining milestones

P0/P1 local implementation is distinct from production rollout. Expand cursor pagination beyond the current 1,500-record workspace window, historical state snapshots, configurable partial-day capacity, richer calendar/task-assignee UX, educator-reviewed portfolio media, and full keyboard/screen-reader dialog testing. Current report PDF is basic Latin text; branded layout, human-readable signatory presentation and Unicode fonts remain polish work. P2 billing/provider milestones remain in `P2_MILESTONES.md`. Hosted identity, storage/restore, legal approval and pilot operational procedures must be validated before real child records.
